# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Docusaurus 3 site for ConCat (concat.app), an event/convention management product. It holds the marketing pages (home, pricing, policies), the end-user guides, and the public API reference. Docs are written in Markdown/MDX; there is no application code or test suite here.

## Commands

Use **npm** (`package-lock.json` is committed). Node `^26` is required.

- `npm install`: install dependencies
- `npm start`: dev server with live reload
- `npm run build`: production build into `build/`. Run this to validate changes: `onBrokenLinks: 'throw'` makes any broken internal link fail the build.
- `npm run serve`: serve the built `build/` directory
- `npm run typecheck`: `tsc` over `src/` and the root JS config files, with every strictness flag on (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, unused-code checks, ...). Docusaurus compiles via Babel, so this is the only type gate. Use `import type` for type-only imports.
- `npm run format` / `npm run format:check`: ESLint (`eslint.config.mjs`) then Prettier (`.prettierrc.json`: single quotes, width 120). Prettier formats code, styles and all Markdown/MDX, including `docs/`. ESLint only lints the JSX in `.md`/`.mdx` through `eslint-plugin-mdx` (both extensions use the MDX parser, as Docusaurus does) with `@stylistic` JSX rules Prettier lacks: self-closing empty elements, `prop="x"` instead of `prop={"x"}`, boolean shorthand, tag/curly spacing. Prettier's MDX parser predates MDX 3, so after formatting content run `npm run build` to confirm it still compiles.
- `npm run clear`: clear the `.docusaurus` cache when the dev server behaves oddly

## Structure

- `docs/guides/`: user-facing guides, shown in `tutorialSidebar`
- `docs/api/`: API reference, shown in `apiSidebar`. Endpoints are split into `endpoints/v0/` (current) and `endpoints/legacy/`.
- Both sidebars are **autogenerated** from folder structure (`sidebars.js`). Ordering and labels come from `_category_.json` in each folder (`label`, `position`) and `sidebar_position` in page frontmatter. Adding a page means picking a `sidebar_position`; adding a folder means adding a `_category_.json`.
- `src/pages/`: standalone React pages (`index.tsx`, `pricing.tsx`, `policy/*`)
- `src/components/`: React components, each with a co-located `*.module.scss`. Global styles live in `src/css/custom.scss` and `_variables.scss` (SCSS via `docusaurus-plugin-sass`). Use the module system, not the APIs Dart Sass 3 removes: `@use '@site/src/css/variables' as *;` (not `@import`) and `color.adjust()` from `@use 'sass:color'` (not `darken`/`lighten`).
- `static/img/`: images, grouped by feature area (e.g. `img/cashier/`, `img/tutorial/`). Reference them as `/img/...`.

## MDX components

`src/theme/MDXComponents.tsx` swizzles the MDX mapper so these components are usable in any `.md`/`.mdx` file **without importing them**: `Highlight`, `Attribute`, `ParentAttribute`, `MaterialIcon`, `Link`, `RestElement`, `RestList`, `EndpointRequest`, `EndpointResponse`, `ExampleBox`, `SplitColumn`, `Card`, `BigButton`, `Admonition`, `Figure`, `TableFigure`, `Sidenote`, `Result`, `Sample`. A new component meant for docs must be registered there. Tags are case-sensitive: a lowercase tag such as `<splitColumn>` compiles to an unknown HTML element, not the component.

`MaterialIcon` relies on the Material Symbols font loaded in `docusaurus.config.js` `stylesheets`, which also loads the platform fonts (Armata, Krona One).

## Textbook style

Guides with `textbook: true` in front matter get the textbook article layout (numbered sections, margin column, numbered figures and tables, step badges with `<Result>` lines). `src/theme/DocItem/Content` adds the `.textbook` wrapper; styles are in `src/css/_textbook.scss`, tokens in `src/css/_tokens.scss`. `docs-style/TEXTBOOK-STYLE.md` is the spec: tokens and how each element is written. Adding or removing a file under `src/theme/` needs a dev-server restart.

## Generated API reference

The v0 endpoint pages in `docs/api/endpoints/v0/reference/` are generated by `docusaurus-plugin-openapi-docs` (with `docusaurus-theme-openapi-docs`, both pinned) from a ConCat instance's Swagger spec. Neither the spec nor the pages are committed; only the hand-written `reference/_category_.json` is. `npm run gen-api-docs` (`scripts/gen-api-docs.mjs`), run by `prestart` and `prebuild`:

1. fetches `$OPENAPI_ORIGIN/api/swagger.json` (default `https://demo.concat.app`; use e.g. `OPENAPI_ORIGIN=http://localhost:8082` for a local master), drops `host`/`basePath`, forces `https`, and writes `static/openapi/concat.json` (also served at `/openapi/concat.json`). If the fetch fails and that file exists from an earlier run, it is reused with a warning; otherwise the build fails.
2. deletes everything in `reference/` except `_category_.json` and runs `docusaurus gen-api-docs concat`. Don't use `docusaurus clean-api-docs`: it deletes `_category_.json` too.

ESLint and Prettier skip the generated files. Handwritten docs that link to reference pages break the build when the instance drops an endpoint (`onBrokenLinks: 'throw'`).

The docs plugin uses `docItemComponent: '@theme/ApiItem'`. Non-API docs fall back to the normal layout, so `src/theme/DocItem/Content` (the textbook wrapper) still applies.

## API reference page conventions

Follow the pattern in `docs/api/endpoints/v0/*.mdx` (e.g. `dealers.mdx`):

- Frontmatter: `displayed_sidebar: apiSidebar` and `hide_table_of_contents: true`.
- The page opens with a `<SplitColumn>`: a description on the left and a `<RestList>` of `<RestElement method path anchor>` on the right. Each `anchor` must match the slug of a `###` heading further down.
- Each endpoint is a `###` heading under `## Endpoints`, written as plain prose with no `<SplitColumn>`: a short description, a bullet list of error cases (logic-error code and name) where it helps, and a closing scope and link, such as ``Scope: `order:manage`. [Full reference](/docs/api/endpoints/v0/reference/remove-order-item)``. Request and response fields and JSON examples aren't repeated, because the generated reference page has them. `<Attribute>`/`<ParentAttribute>` and `<EndpointRequest>`/`<EndpointResponse>` are now used only on hand-written pages outside v0: the OAuth guide, webhook events, errors and the legacy users page.
- `Attribute` `id`s must be unique within the page, so they start with a short prefix for the page (e.g. `oauth-`, `wh-`, `user-`), usually extended by the endpoint or section, as in `oauth-req-client_id` or `user-current-retrieve-resp-id`.
- There are no shared model partials. Each v0 page describes its object once, in a `## The <name> object` section (e.g. "The dealer object"), and each endpoint links to its generated page for the full request and response schemas: `[Full reference](/docs/api/endpoints/v0/reference/<operation>)`.

## Trial signup page

`src/pages/trial.tsx` posts `{ country, email, firstName, lastName, orgName }` as JSON (CORS) to `${onboardingApiOrigin}/api/signups`, with the reCAPTCHA v2 token in the `g-recaptcha-response` body field (a custom header would fail the backend's CORS preflight). Both values come from `customFields` in `docusaurus.config.js`, which reads `ONBOARDING_API_ORIGIN` and `RECAPTCHA_SITE_KEY` at build time. `country` is an ISO 3166-1 alpha-2 code from the static list in `src/data/countries.ts`. That list is static so server and browser render identical names; don't switch it to runtime `Intl.DisplayNames`. Helper modules must not live in `src/pages/`, because every file there becomes a route.

## CI & deployment

GitHub Actions (`.github/workflows/ci.yml`) runs `npm run format:check` (ESLint + Prettier), `npm run typecheck` and `npm run build` on pushes to `main` and on every PR, using the Node version from `package.json` `engines`.

The site is hosted on Cloudflare Pages. When `CF_PAGES_BRANCH` is set to anything other than `main`, `docusaurus.config.js` adds a red "preview version" announcement bar. `deploymentBranch` is `deployment` (used by `npm run deploy`). Commit messages follow Conventional Commits with a feature scope, e.g. `feat(products): ...`, `fix(api): ...`.
